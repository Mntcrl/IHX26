# PHØTON threat and trust model

Scope: Galaxy v1 protocol (`galaxy/v1`), policy `galaxy-pc-v1m`, XRPL Testnet. See the [specification](../protocol/galaxy-v1-spec.md), [trust-model decision](../adr/0006-trust-model.md) and [code-level review and remediation](review-2026-11-21.md).

What a positive result means: the photograph's canonical raster is bound to a CAPTURE published by a registered (App Attest) app instance, and a Groth16 proof shows that the committed sensor evidence, opened at positions chosen by a ledger after the commitment, satisfies the public physical-consistency policy. It does **not** prove that the scene is real, that the sensors were not fed synthetic data, or that the photo depicts what a viewer believes it depicts.

## 1. Trust sources and what each one gives

| Source | Gives | Does not give | How it is used |
|---|---|---|---|
| XRPL consensus | Total order, inclusion and timestamps (ledger close time) of validated transactions; immutability of published memos; enforcement of each account's `AccountTxnID` (a transaction naming a different predecessor fails with tefWRONG_PRIOR) | Confidentiality; interpretation of Galaxy payloads; unbiased randomness | CAPTURE/PROOF ordering, deadlines, challenge ledger hash, append-only registry, own-transaction chain of device registration accounts (spec §12) |
| Ledger data availability | Access to historical transactions | Guarantee that any given server keeps full history; bounded work when third parties add transactions to an account's history | Verification needs the ledgers L0…Lproof and three history windows of the registration account: A = [DEVICE manifest ledger, L0] (counters, capture_id uniqueness, re-challenge), B = (Lsel, min(deadline, latest)] (PROOF candidates), C = [DEVICE manifest ledger, latest] (REVOKE). Missing history, an exhausted work budget or a broken `AccountTxnID` chain → UNAVAILABLE, never VERIFIED |
| RPC endpoint | Convenient access to the ledger | Independent assurance: a remote server answering `validated: true` is trusted, not verified | One endpoint (URL) per verification; if the result is UNAVAILABLE the whole verification restarts with the next configured endpoint. Answers are never mixed and never cross-checked; the report names the endpoint and `rpc_trust: remote | local`. Bound to the requested hash: transactions fetched by hash (CAPTURE, DEVICE/CIRCUIT manifests, exact PROOF, every `AccountTxnID` walk step). Bound to the account's Ed25519 master-key signature: every Galaxy record taken from `account_tx` (history, bundle chunks); other rows are ignored and counted. RPC claims only: `validated`, TransactionResult, TransactionIndex, ledger index, ledger hashes and close times, `complete_ledgers`, completeness of `account_tx`, the AccountRoot `AccountTxnID` at the latest ledger, and metadata `PreviousFields.AccountTxnID` links. A locally operated rippled removes the dependency on a remote provider (it still trusts the validator list it is configured with) |
| Galaxy discovery nodes | Hints: photo_id → candidate captures, cached reports | Any influence on validity | Contacted only after explicit opt-in (web consent checkbox; CLI `verify --lookup` or `galaxy lookup`). Every hint is re-verified from XRPL; non-binding hints are discarded; nodes can only hide data (availability), not create validity |
| Groth16 (BN254) + setup | Succinct proof that a witness satisfies the circuit | Soundness if the setup's toxic waste is known | The verifying key is trusted only from explicit accepted-circuit configuration (circuit_id, vk_digest, policy_id, registration_tx). The verifier reports `proof.ceremony` but does not enforce a ceremony class. The shipped Testnet config accepts circuit `a0bed7f1…` (policy `4ad25185…`), whose key comes from a `development-single-party` setup and is **not production-trusted** |
| Apple App Attest | Key bound to a genuine Apple device and to the app identity (team + bundle id), assertion counter | Integrity of the sensor data path at capture time; that the app was not instrumented at run time beyond Apple's checks; per-sample sensor authenticity; a limit on the number of keys or registrations per device | Registration (attestation) and per-capture assertions verified locally against the pinned Apple root. Development and production environments are distinct classes. Development-environment credentials come from debuggable builds signed by the team (including free teams): they attest the app identity, not its integrity. The shipped Testnet config accepts both; production configs should accept `production` only. Dev-unattested credentials never yield VERIFIED |
| Physical sensors (ARKit depth, poses, IMU) | Measurements as produced by Apple frameworks (sceneDepth is a fused estimate, not raw LiDAR) | Proof of physical provenance | The circuit checks consistency of committed data; Bluetooth, noise and meta aggregates are committed only |

## 2. Assets
- Integrity of the image ↔ evidence ↔ proof binding (photo_id, rgb_root, evidence_root, capture_id, challenge, proof).
- The photographer's XRPL wallet seed and App Attest key (device Keychain / Secure Enclave).
- Private evidence (frames, depth, poses, IMU, aggregates), salts and witnesses (device only).
- Verifier users' photos (never leave the browser) and their lookup privacy.
- Accepted-circuit configuration (the root of VK trust).

## 3. Threats, controls and residual risk

| Threat | Controls | Residual risk |
|---|---|---|
| Modified photograph (edit, crop, resize, recompression) | photo_id over the exact canonical raster; rgb_root recomputed from pixels; strict PNG/JPEG profiles | Lossless re-encodings that keep the raster verify by design |
| Metadata substitution (references to another capture) | XMP is untrusted; CAPTURE must bind photo_id and rgb_root of the presented image | None for validity; wrong references only cause INVALID/NOT_FOUND |
| Reused or substituted LiDAR/RGB (commitments to unrelated data) | All evidence committed before the challenge; Merkle openings in-circuit; RGB–depth edge check; temporal reprojection; camera/IMU in evidence_root | **Measured weakness:** on synthetic scenes, depth from another scene with the same RGB passes v1m in 16/20 seeds ([report](../experiments/synthetic-v1m.md)); v1m does not reliably detect this substitution |
| Screen / print / projection recapture | Global and central planarity limits, distributed non-planar evidence, RGB–depth correspondence, parallax | Synthetic: flat/tilted/curved screens and prints rejected 20/20; a centre screen surrounded by real objects passed 2/20 (per challenge; see re-challenge row); physical-device experiments still pending |
| Synthetic but internally coherent sensor data (compromised acquisition or device) | App Attest limits the code identity; capture flow commits before the challenge | **Not prevented:** a fully synthetic, coherent dataset fed into the pipeline can satisfy the proof |
| Unconstrained or under-constrained circuit | Constraint-level negative tests; every private value read by a policy predicate is range-bound (leaf bytes 8/16/2 bit, camera 26/32/48 bit, IMU 32 bit, positions 6 bit); committed-only aggregates and Merkle siblings are opaque field elements bound by Poseidon; code review | Residual until an independent audit; any soundness bug can make invalid evidence provable |
| Malicious verification key / permissive circuit published on XRPL | VK accepted only from explicit configuration with vk_digest; circuit registrations are not trusted by themselves | A user who adds an untrusted circuit to their config accepts its policy |
| Groth16 setup compromise | VK accepted only from explicit configuration; the verifier reports the ceremony class but does not enforce it; production requires a multi-party phase-2 ceremony with verifiable contributions (not yet run) | The shipped Testnet config accepts the development single-party key of circuit `a0bed7f1…`: whoever ran that setup could forge proofs for it |
| Proof replay / swap | Public inputs reconstructed from CAPTURE + selection ledger; PROOF bound to manifest tx, selection ledger and circuit; same account (master-key signature verified) and a nonzero signed `AccountTxnID`; window Lsel < Lproof ≤ Lsel + w_proof; first valid proof in ledger order wins; an advertised PROOF cannot select itself | None known |
| Assertion replay / credential misuse | Assertion over core299 (incl. nonce, network, account, Lpre); counter strictly increasing per registration in ledger order (window A); capture_id uniqueness (window A); DEVICE manifest and CAPTURE must sign a nonzero `AccountTxnID` (`registration.txn_chain`, `capture.txn_chain`); master-key-signed REVOKE (window C, backdating allowed, future dates ignored) | Historical checks rely on the RPC for completeness of windows A and C. The `AccountTxnID` walk binds each step to a signed predecessor, but the walk start for windows B/C (AccountRoot at the latest ledger) and metadata links of own non-Galaxy transactions are RPC claims |
| Network confusion (Testnet vs Mainnet) | network_id inside CAPTURE/PROOF and checked against server_info; mainnet refused unless allowed | None known |
| Ledger sampling manipulation / re-challenge | One challenge per CAPTURE (Lsel = L0 + `sel_offset`). A CAPTURE whose photo_id, rgb_root or evidence_root equals that of an earlier CAPTURE of the same account in window A is INVALID (`capture.unique`), across registrations of that account; in lookup mode the earliest XRPL-authenticated CAPTURE that binds the photo, across registrations and accounts, decides and later ones are only listed; the iOS core issues one CAPTURE statement per ingested evidence object | Ledger hashes are not an unbiased beacon (validator influence). Re-challenge remains possible in direct/manual mode from a different account, or from an earlier CAPTURE that predates the current registration's DEVICE manifest (outside window A); lookup cannot exclude earlier CAPTUREs omitted by the consulted nodes; a near-identical pixel variant plus re-salted evidence is a new photo; selective abort (not publishing a PROOF) is always possible. For a credential holder, per-challenge false-accept rates are therefore per attempt; App Attest (production app behaviour) is the only limit on attempts |
| Malicious RPC endpoint | Transactions fetched by hash are bound to that hash; history and chunk records must carry a valid Ed25519 master-key signature of the registration account (others are ignored and counted); the `AccountTxnID` walk follows signed links; network_id checked; one endpoint per verification with a full restart on UNAVAILABLE; local rippled supported | A remote endpoint can lie about `validated`, TransactionResult, TransactionIndex, ledger hashes and close times, history completeness and AccountRoot/metadata links, and can hide records: this forces UNAVAILABLE, or VERIFIED if it hides an earlier re-challenge CAPTURE or a REVOKE. It cannot forge Galaxy records. Endpoints are not cross-checked (failover is not a quorum), and a public URL may be served by several load-balanced servers. v1 does not verify validator signatures over ledger headers; only one's own rippled removes the remote trust |
| Third-party history inflation (anyone can send transactions that appear in a registration account's `account_tx`, e.g. Payment, TrustSet, EscrowCreate, SetRegularKey toward it; DepositAuth does not stop all of them) | Only master-key-signed Galaxy records of the account count; two bounded scans (A, and one shared B/C scan from the latest ledger down to L0 that reuses A's REVOKE records), each with an `account_tx` budget (64 pages × 200 rows); above it the verifier walks the account's own-transaction `AccountTxnID` chain (budget 4,096 steps, CLI up to 65,536), which third parties cannot lengthen; one server_info per endpoint attempt. Testnet: 201 third-party Payments left the verdict unchanged | Inflation forces the slower walk permanently for scans that contain it. The shared B/C walk covers every own transaction after the CAPTURE, so a registration account whose own activity after a capture exceeds the walk budget, or the time limit (one sequential RPC round trip per step; CLI 300 s, node 120 s), makes that capture UNAVAILABLE. Mitigation: bound own activity per registration (rotate registrations/accounts) |
| Malicious / Sybil discovery nodes | No quorum; every hint re-verified; non-binding hints discarded; SSRF guard, timeouts, size limits; node rate limits per IPv4 address or IPv6 /64 with least-recently-seen eviction at 4,096 clients, headroom reserved across IPv4 /24 and IPv6 /56 and /48 prefixes, and a node-wide budget; `X-Forwarded-For` honoured only from configured trusted proxies and only as a single address; verification jobs use their own RPC budget, per-registration fairness and persisted exponential backoff (60 s to 6 h) | Nodes can hide captures (availability, censorship) and observe queried photo_ids. Clients spread over many /48 prefixes can still exhaust the node-wide budget |
| Oversized / malformed payloads and images | Strict bounded decoders, dimension checks before allocation, bundle and response caps; property-based tests (proptest, `crates/galaxy-security-tests`) over the wire formats, XRPL codec, PNG/JPEG and XMP, App Attest CBOR/DER, GXRW/GXEV and node lookup responses | No coverage-guided fuzzing yet |
| Unavailable historical data | UNAVAILABLE state with consulted ranges and history-work counts (`history.complete`) | Long-term verification depends on independent XRPL archives |

## 4. Privacy
- Never published: images, frames, depth, poses, IMU samples, Bluetooth observations, salts, witnesses.
- Public and correlatable by anyone: photo_id (anyone holding the photo can test membership), capture time (ledger), wallet address, App Attest key id and registration, device model class if included in public material, circuit/policy ids.
- Bluetooth: foreground scan only, session-random HMAC dedup, identifiers discarded after aggregation; the aggregate is a commitment, not a proof of nearby devices.
- Browser verification: decoding and verification run locally; photo_ids go to discovery nodes only after the consent checkbox (a restart on another XRPL endpoint repeats the lookup to the same nodes).
- CLI: photo_ids go to nodes only with `galaxy verify --lookup` or `galaxy lookup`; configured nodes (`--node`, `GALAXY_NODES`) are otherwise unused.
- XRPL endpoints learn the queried transaction hashes, the photographer's account (`account_tx`, `account_info`) and the ledger indexes; they can link lookups to captures. After a restart, the next endpoint sees the same queries.

## 5. Operational security notes
- Seeds: iOS Keychain (this-device-only) / `~/.config/galaxy/` for development wallets; never in git, logs or memos.
- Test device data: see the [2026-11-20 incident](../incidents/2026-11-20-device-container-deletion.md) and spec §19 device data safety rules.
